# 监测新鲜度与零新增排查

“立即刷新”执行来源采集、AI 范围分类、主库增量消费和资料同步。各层数字含义不同：来源新增记录可能与 AI 无关，也可能是已有 CVE 的另一个来源；只有新的 AI 阳性 CVE 才增加主库的“AI 情报新增”。

`GET /api/monitor/status?light=1` 的 `collection_summary` 与本轮 `POST /api/monitor/run` 返回相同的来源摘要；`last_count` / `count` 仍表示主库新增 AI CVE。摘要保留成功、部分完成、失败、跳过来源，以及已确认提交的来源记录计数。`counts_complete=false` 时，该计数不是全源完整总量；超时没有返回计数时为 `null`，不是零。无来源刷新的一轮会清除上一轮摘要，避免将历史来源结果冒充当前结果。

排查顺序：

1. 看来源状态和错误。GitHub 403 且额度耗尽属于采集失败；不能解释为成功空轮。GitHub 全局公告和厂商公告均读取 `GITHUB_TOKEN` 或 `GH_TOKEN`，显式构造参数仍可覆盖。凭据只能配置在本机环境或部署密钥中，不提交到 Git。
2. 看来源记录新增、修改与主库 AI 新增。分类为非 AI 的记录仍保留在原始库；需要语义复核的 `pending_llm` 不等于已确认 AI 情报。B 的语义分类配置独立于网页问答模型配置，零模型预算不会自动清空待复核项。
3. 看历史游标和采集中断。最新发布窗口优先采集；历史修改游标落后不等于最新发布通道必然落后。但停机、定时任务未执行、网络失败可能产生缺口，必须检查真实采集日志，不能仅凭 15 分钟配置声称延迟达标。
4. 对照精确的来源时间和首次采集时间。带明确时区的完整时间转换为北京时间；无时区时间明确标注，原始日期不补造小时。首次回补、只有日期的文档、论文投稿时间等不能混为实时采集样本。

本机与 Docker 在线刷新默认单来源 120 秒、全轮 600 秒。原 45 秒单来源配置在预留 SQLite 提交时间后，仅有约 22.5 秒供 NVD/GitHub 查询，容易耗尽预算。自动轮询为一轮结束后再等待配置间隔；电脑休眠、程序退出期间不会采集。延长超时只为成功请求预留空间，不保证第三方服务随时可用，也不改变原始首次采集时间。

NVD 与 GitHub 先抓最近 12 小时，再用独立的发布游标追补遗漏窗口，最后追补历史修改。已有发布游标会跨轮恢复，失败和分页不完整都不推进。旧库首次升级固定一个七天的发布回补起点，单轮默认至多四个六小时窗口、六次请求、25 秒且不超过剩余网络时间的一半；余量留给历史修改。该起点是回补范围，不代表之前已经采集完整。最近窗口成功也不能跨过未补齐的旧缺口。统计中的 `publication_recovery` 和 `backfill` 分别表示发布与修改追补。

刷新后的来源摘要可用于发现失败；连续新鲜度验收仍需保留真实历史和固定观察窗口，不能以一次成功或缩短定时间隔代替。
