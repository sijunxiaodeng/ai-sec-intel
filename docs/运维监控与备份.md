# 运维监控与可校验备份

系统已有持久处理队列、租约超时重领、指数退避、失败任务重试、容器退出后重启和 API 健康探针。本次补齐可选 Prometheus/Grafana 配置与主应用/C 证据库的备份恢复工具。配置文件存在、离线验收通过和真实线上启用是三种不同证据。

## 启用可选监控

先按 [正式数据部署与交付](正式数据部署与交付.md) 选择 Actions 或常驻采集模式。在机器本地 `.env.production` 中设置独立的 `GRAFANA_ADMIN_PASSWORD`，然后为当前模式叠加监控配置。例如，已选择 Actions 时：

```bash
docker compose --env-file .env.production \
  -f docker-compose.actions.yml -f docker-compose.observability.yml \
  up -d --build
```

常驻采集模式将第一份配置替换为 `docker-compose.production.yml`。两个正式采集模式不能同时启动。监控本身没有采集写入端，也不触发富化或问答。

Grafana 位于本机 `http://127.0.0.1:3000`，首次账号为 `admin`，密码使用本地设置值；Prometheus 为 `http://127.0.0.1:9090`。默认只绑定回环地址。Grafana 自动加载中文运行证据仪表盘，Prometheus 持久保存最近 30 天序列，监控容器日志限制为每份 10 MB、最多三份。

`scripts/ops_metrics.py` 是独立、仅依赖 Python 标准库的 exporter。它并行读取 B 的 `health/coverage/metrics` GET 接口，以 SQLite `mode=ro` 查询主库已存在的 `processing_jobs`；不调用会初始化队列表的处理状态接口，不创建数据库或表。没有数据、接口失败或表未建立时，输出相应证据可用状态为 0，实际时延/队列指标保持缺失；不会给未知情况填上“零积压、零延迟”。`/healthz` 仅表示 exporter 进程能响应，采集证据可用性需查看 `ai_sec_probe_success`。

仪表盘覆盖当前有效 AI 内容类别、最新采集尝试成功比例、来源新鲜度、当前 AI 正例与全记录分别统计的发布到首次入库 P95、持久队列积压和重试耗尽任务。来源的空成功轮询只证明接口调用成功，不能增加内容覆盖；初始样本不足时图表显示“暂无证据”。问答 QPS/端到端响应时间尚未埋点，明确报告 `ai_sec_qa_metrics_available=0`，不把 exporter HTTP 时延当成问答时延。

Prometheus 已配置 exporter 不可达、证据接口失败、来源过期/失败、任务重试耗尽、积压和队列证据不可用等规则，可在 `/alerts` 查看触发状态。当前没有 Alertmanager 或邮件/即时通讯通知配置，自动向外部人员发消息仍需实际通知服务与接收方配置。本次没有替用户启动正式服务器或声称已上线监控。

## 主应用与 C 的备份和恢复

新增 CLI `scripts/backup_state.py` 覆盖同一数据目录中的 `knowledge.sqlite3`、`task_c.sqlite3`、`library.sqlite3`，以及已存在的资产登记、资产观测、PoC 来源、论文查询轮转数据库、卡片导出、监测状态和旧 JSON 迁移输入。使用 SQLite backup API，将已提交 WAL 页纳入独立数据库副本；不直接拷贝活动 WAL/SHM 或锁文件。每份数据库执行 `quick_check`，清单记录文件大小、SHA-256 和表名。默认排除模型设置、环境密钥和日志；Linux 备份目录权限 700、文件 600。

先停止主应用/C 的写入进程；B 可以继续采集。`--quiesced` 记录操作者已暂停这些写入的声明，工具不会自动停止进程；多库同一逻辑切面的前提是整个备份期间保持暂停。单个 SQLite 的一致性备份不能证明多个仍被修改的库一致。以主库实际所在目录替换以下示意路径，在能读取该目录的主机或容器执行：

```bash
python scripts/backup_state.py backup \
  --source /path/to/main-data --destination backups/main-20261014 \
  --quiesced
python scripts/backup_state.py verify --source backups/main-20261014
python scripts/backup_state.py restore \
  --source backups/main-20261014 --destination /path/to/restored-main-data
```

`--destination` 必须尚不存在；恢复始终写入新的目录，校验成功后才整体发布，不覆盖正在使用的数据。Linux 使用 `renameat2(RENAME_NOREPLACE)`、Windows 使用拒绝已有目标的 rename，防止校验后并发出现的目标目录被替换；其他平台或缺少该 Linux 接口时拒绝发布。校验失败不留下可误用的半份恢复结果。恢复后在隔离实例把 `MAIN_DATA_DIR` 指向新目录，核对漏洞、资料、持久消费游标、处理队列和问答索引；确认无误后再切换正式卷或挂载。恢复会保留原持久任务状态，过期租约由现有处理程序重领，不擅自清空失败历史。

如果使用 Docker 命名卷，可将当前 `main-app` 的卷作为只读 `/source` 挂载到同一已构建的主镜像，并额外挂载本地备份目录到 `/backup`，在该临时容器执行以上命令；暂停主应用后再读取。准备备份目录时应使执行用户可写，备份完成后继续保持私有权限。不要用 `down --volumes` 清除原卷。

模型设置默认需要在恢复实例重新配置。确实要保留数据目录中的 `model-settings.json` 时可显式增加 `--include-settings`；这份备份可能包含 API 凭据，应存放在受控的备份存储中，不能上传为公开 Actions artifact。正式默认模型配置是 `config/local.json`，不在本工具范围；`APP_SETTINGS_PATH`、`MAIN_KB_DB_PATH` 以及某些资产/论文/PoC 模块的独立默认路径也可能位于所选目录之外。需检查实际配置，分别做同样的私有备份，并在恢复时绑定原路径。校验清单用于检测损坏，不能替代受信任备份来源或离机备份存储。

B 的采集库、原始逐源数据、监测基线和快照代际由现有 `intelligence/deployment/actions_state.py` 一致性快照/校验恢复机制单独处理；Actions 镜像卷包含不可变代际，可重新拉取经过身份和完整性校验的 artifact。只备份主应用目录不能恢复 B 的历史或证明云端交付完整。正式备份计划还需实际备份位置、定期调度、保留周期和恢复演练记录。

## 已完成的可复现检查

新增测试检查真实回环 HTTP 部分失败、未知指标保持缺失、只读队列不初始化业务库、AI 与全记录时效分离；备份测试覆盖三库恢复、已提交 WAL 纳入副本、默认排除密钥、损坏/额外文件/符号链接拒绝、原目录不覆盖和空库不初始化。

```bash
python scripts/run_offline_tests.py --start-directory scripts/tests --pattern 'test_ops_*.py'
```

CI 对两种正式模式的可选监控 Compose 配置执行解析校验，并用官方 Prometheus 镜像的 `promtool` 校验配置和告警规则。此类软件检查不代替真实生产观察、七天连续运行、独立质量评测、实际备份恢复演练或问答负载测试。
