# 通用证据推理

资料问答保留默认的 `excerpts` 摘录模式。需要跨文档分析时，向
`POST /api/library/ask` 传入 `mode: "reasoning"`：

```json
{
  "question": "这项删除机制与另外一份审计保留规范结合后，哪些数据仍会保留？",
  "mode": "reasoning",
  "use_model": true,
  "document_ids": []
}
```

使用系统已有的模型配置。`document_ids` 可选，最多指定四份存档资料；
`document_type` 可用于限制类型。具体 CVE 的受影响范围和修复问题继续路由至漏洞问答。

## 实际执行流程

1. 在本地资料库检索原问题，检查资料完整性。
2. 模型根据问题和初始证据分解至多三个子问题，指出名称歧义及缺失前提。
3. 程序对这些子问题继续执行本地检索，可以找到初始结果中没有的资料。
4. 模型生成事实、证据推断或条件性推断。每条结论必须提供已有证据编号及连续原文。
5. 程序检查编号、原文和输出结构，再以第二次模型评估检查语义支持、版本、否定、适用条件及来源冲突。
6. 只展示通过检查的结论。冲突来源不用于确定结论；缺少实体、版本或条件时提示补充信息。

模型没有任意工具权限：它只能返回子问题和结构化分析，程序只执行预定义的本地检索。
主题不需要预先写入主题枚举。最多保留十六条证据，每条给模型的正文上限为 2400 字符；
这是有界检索，不能宣称已检查所有文档的每个段落。

## 如何检查结果

- `reasoning_status`：`answered` 表示流程完成；`partial` 表示存在缺前提、冲突或被拒绝结论；`fallback` 表示只展示摘录。
- `reasoning_trace`：记录实际检索查询、检索方式、新增证据数量和核验结果。
- `reasoning_claims`：逐条结论、类型、尚未证实的条件，以及每项对应的引用和原文。
- `conflicts`、`ambiguities`、`missing_premises`：记录尚无法确定的内容。
- `used_model`、`model_attempted`、`fallback_reason`：区分模型是否被尝试、是否成功用于最终推理，以及回退原因。

三个模型请求共享五秒时间预算。预算用尽、模型未配置、请求失败或输出不合规则回退原文摘录，
不会把摘录标为完成推理。该预算不等于已证明整次 HTTP 请求小于五秒：检索、渲染和网络调度也占时间，
需要使用实际部署及独立问题集测量端到端延迟。

## 验收边界

程序可以检查引用存在、原文一致和结构完整；语义支持由模型复核，仍可能判断错误。
`verdict.semantic_accuracy_measured` 固定为 `false`，流程通过不代表达到赛题准确率。
接口字段、摘要、目录有明确来源范围提示，不能作为原始全文使用。

`questions/test_general_reasoning.py` 使用未登记的虚构主题验证多次检索、引用伪造拒绝、
冲突、缺前提及失败回退，属于软件回归检查。它不属于独立标注验收集，也不产生业务准确率。
正式验收应由未参与实现的人先标注真实问题的答案及证据，再记录实际模型、运行版本、
结论正确性、引用支持和总响应时间；保留失败及回退样本，不只统计成功输出。
