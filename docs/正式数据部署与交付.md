# 正式数据环境与 Actions 交付

演示和正式数据分开。默认 `scripts/demo-up.sh` 使用 `docker-compose.offline.yml`（无 Docker 时使用 `scripts/offline_demo.py`），首次生成 5 条合成漏洞和 7 份合成资料，重复启动保留数据。外部网络和模型调用关闭，数据库及模型设置均保存在独立演示目录/卷。首次安装依赖或构建镜像仍需要包下载网络。

原 `docker-compose.yml` 保留联网演示与联调用途，脚本需显式指定 `DEMO_NETWORK=online`；种子只写演示卷。正式配置没有种子服务，主应用禁止自动导入示例卡片。

## 选择一个采集写入端

| 场景 | 启动配置 | 唯一采集写入端 | B API 读取的数据 |
|---|---|---|---|
| 有持续在线的机器 | `docker-compose.production.yml` | `b-monitor` | 同一个 `b-production-data` 卷中的 SQLite |
| 继续用 GitHub Actions | `docker-compose.actions.yml` | GitHub `main` 工作流 | `b-mirror` 校验交付的不可变 SQLite 快照 |
| 离线演示 | `docker-compose.offline.yml` | 首次合成样例初始化 | 独立离线演示卷 |

这些模式分别使用独立数据卷。不能把正式在线配置与 Actions 镜像配置合并启动；两个正式配置也占用相同端口。程序额外在卷中写入 `.writer-mode`，拒绝采集器与镜像器共用写入目录。B API 本身使用 SQLite 只读连接。

## 当前没有服务器：继续用 Actions

1. 将修复合并到 `main`。工作流只在 `main` 执行，并固定拉取该次运行的 `github.sha`，不再读取旧的 `feat/intelligence` 运行代码。
2. 启动一次新的工作流。它恢复已有状态，升级数据库并发布带代码 SHA、workflow、run number 的快照。旧快照仍可供采集器迁移，镜像器拒绝发布缺少上述信息的旧快照。
3. 在需要运行网页/API 的机器上复制 `.env.production.example` 为 `.env.production`，文件权限设为 `600`。只在本地填写 `GITHUB_TOKEN`：细粒度 token 仅选择该仓库，授予 **Actions: read** 和自动附带的 Metadata read。不需要仓库写权限，不要把 token 提交或发到聊天中。
4. 执行：

```bash
bash scripts/production-up.sh actions
docker compose -f docker-compose.actions.yml logs -f b-mirror
```

`b-mirror` 每 60 秒检查一次最新已完成的采集运行。它核对同仓库、固定 workflow ID、`main`、事件类型和 artifact run ID，再校验清单 SHA-256、文件大小、SQLite 完整性、采集代码 SHA 和运行编号。新一代不得丢失旧记录、推迟已有首次入库时间或重启原观察基线。只有全部验证通过才原子切换 `current`；B API 的后续请求读取新一代，已经打开的只读连接可以完成旧一代请求。

交付失败时保留上一份已经验证的数据，不用空库替代。安全状态保存在卷中的 `mirror_status.json`，包括 `ready/degraded`、运行编号以及是否仍提供旧数据。每次成功交付后保留最新八代本地快照。API 的数据库可用不等于数据新鲜；必须同时查看镜像日志、最新云端运行、来源健康及实际时效。

**关机后 GitHub 仍能采集，但关闭的电脑不能提供网页/API。** 电脑重新开机并启动本配置后会自动获取最新可信快照；要让网页/API 全天在线，仍需要一台持续运行的机器。GitHub runner 不被当作常驻服务器，镜像模式没有本地采集进程。

## 有持续在线机器：共库采集

```bash
bash scripts/production-up.sh collector
docker compose -f docker-compose.production.yml logs -f b-monitor
```

`b-monitor` 每 15 分钟运行一轮，各来源独立超时；它和 `b-api` 使用同一个持久卷 `/app/data`。B 采集器唯一写库，API 只读。主应用正式模式只接收团队 B 的统一筛查结果，不另行从 A 的 NVD/OSV 入口绕过筛查；新增情报自动进入后续任务队列。

既有正式数据库应先停止旧写入端，并备份 DB、基线和状态，再使用已有 `deployment/actions_state.py` 的一致性备份/校验恢复功能迁移。不要通过演示 `--force` 初始化正式卷，不要使用 `down -v` 删除正式数据或时效证据。

停止当前模式会保留卷：

```bash
docker compose -f docker-compose.actions.yml down
# 或：docker compose -f docker-compose.production.yml down
```

## 验收边界

先验证真实数据链：云端新增记录 → 快照上传 → 镜像确认对应 run/SHA → B API 可查询 → A 的增量消费游标推进 → 富化和索引任务完成。用另一次运行的内容变更再次确认更新，而不只检查 HTTP 200。

旧 `first_seen_at`、逐源观察基线、首次云端部署 `2026-10-09T12:05:16Z` 和历史超时记录保持不变。GitHub cron 仍可能延迟；部署、交付和 API 启动成功不能替代 `<6h` 的真实发布到首次入库评测。正式指标应另外记录云端采集延迟与快照交付/消费延迟。
