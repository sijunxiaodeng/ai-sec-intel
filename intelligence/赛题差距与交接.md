# 赛题九：B 模块现状、差距与团队交接

本文依据赛题九 PDF 和当前 `feat/intelligence` 代码整理。用户当前目标是实际覆盖 **至少 7 类 AI 安全情报**，且漏洞监测延迟 **严格小于 6 小时**。B 默认来源配置为 11 个来源、8 类内容，真实入库已覆盖八类主题，CVE 与非 CVE 文档均可独立查询。恢复采集记录存在六小时超限样本，严格时效验收尚未通过；团队主流程接入仍待 A/C 完成。本文区分已实现、离线已验证和线上待验证，不据接口数量或测试数量推算得分；真实快照见 [运行验证.md](运行验证.md)。

## 2. 八类内容的划分及真实覆盖验收

| 内容类别 | 默认来源 | 计数依据 |
| --- | --- | --- |
| 漏洞数据库 | NVD、GitHub 全球 Advisory | 结构化漏洞条目；两来源计一类，全球 Advisory 不重复充当社区或厂商来源 |
| 安全社区 | Hugging Face 社区安全主题帖子 | 独立持续采集的社区内容，不从已有漏洞参考网址推算 |
| 厂商公告 | vLLM、Ollama、LangChain 仓库 security-advisories | 保留项目/厂商发布来源证据，三个项目合计一类；与全球 Advisory 的重复公告不能夸大独立内容数 |
| 技术博客 | Trail of Bits AI 安全博客 feed | 来源博客文章，经本地 AI 与安全主题过滤 |
| 学术论文 | arXiv AI 安全查询 | 来源论文 ID、摘要、原文 URL 和提交/更新时间证据 |
| 技术标准 | NIST CSRC 正式 AI 标准、指南等出版物 | 从官方目录发现正式文档并读取详情，项目导航页本身不算标准 |
| 政策法规 | Federal Register AI 安全、治理及隐私主题文档 | 官方文号、摘要、原文与发布日期，不把一般 AI 经费新闻充当安全政策 |
| 政府告警 | CISA KEV | 政府维护的已被利用风险目录；收录时间与漏洞发布日期分开 |

RSS、API、网页是获取方式，不是内容类别。来源目录、源 API 数量、数据库总条数及成功空轮询均不能证明七类真实覆盖。`GET /api/intelligence/coverage` 分别给出配置类数、实际入库类数和 `observed_ai_category_count`；至少七类 AI 相关真实内容才满足当前覆盖目标的数量部分，还要逐类审核内容和来源独立性。

CVE AI 覆盖只计当前内容哈希和分类器版本匹配、已完成分类的正例，待复核不混入默认输出。文档数量来自本地主题过滤候选，不等于人工证明的准确率。自定义 JSON 会替换默认目录，API 和监测须使用同一配置，少于七类时报告必须如实显示。

部分厂商 GitHub 页面或公开原始文档已用于检查来源存在性，不能因此保证所有 feed/API 端点可达或字段长期兼容。arXiv 默认按最近 7 天 `submittedDate` 查询并重查近期论文，尚不覆盖所有旧论文的新修订；RSS 保留窗口、页数/条数限制和 NIST 目录发现范围也需用真实结果核验。

## 3. 当前限制：持续可用性与线上时效证据

当前实例已成功采集八类真实内容，先前的整体网络阻断已不再适用于现状。CISA 主站返回 403，采集器使用 CISA 维护的官方 GitHub 镜像；arXiv 首次采集 318 条后后续轮次出现超时，已有文档保留。NVD 与 GitHub 近期新发布阶段成功，历史修改窗口仍在回填。内容覆盖已具备数量证据；尚不能证明持续在线、完整性、分类准确率或六小时时效。失败窗口不得推进增量水位，不能通过关闭 TLS、伪造响应或跳过窗口获得成功状态。

默认目录需要以下九个域名，前八个网络增补已保存到环境配置草稿，GitHub 原始文件域名已在预设中：

```text
services.nvd.nist.gov
api.github.com
www.cisa.gov
discuss.huggingface.co
blog.trailofbits.com
export.arxiv.org
csrc.nist.gov
www.federalregister.gov
raw.githubusercontent.com
```

**安装、启动、两仓库挂载和网络配置已保存为草稿，仍需在环境设置保存并发布，才能在新实例复用。** 发布不由代码脚本执行，已验证的当前实例不等于验证了新任务恢复。新增模型或自定义来源还需对应域名。逐源检查成功/失败/超时/积压、实际内容、来源原文、日期精度和游标；公开 Git 读取可用不代表所有 API 有同样权限，主站 `403` 也不直接说明需要新 Token。

### 严格小于六小时的验收口径

当前目标严于赛题 PDF 的“≤6 小时”：按原始秒数 `delay < 21600` 才达标，`delay >= 21600` 都是违约，等于六小时也不能算成功。显示时四舍五入的小时数不参与判定；使用指标的 `under_6h/breached_6h`，兼容字段 `within_6h` 不能证明当前严格目标。

漏洞时效计算“原始漏洞发布时间 → 系统首次入库时间”。`GET /api/intelligence/metrics` 按 CVE 汇总；`GET /api/intelligence/coverage` 另提供逐来源的观察基线、健康和实时精确样本延迟。逐来源指标包含尚未完成 AI 分类的记录，不测量分类、富化、索引或问答完成时间，不能替代团队端到端时效。

基线只标记首次观察起点，不证明此后持续在线。仅将基线后发布且首次入库、时间精确可信的记录作为实时样本；历史回填单独列出。CISA `dateAdded`、仅日期、缺少时间/时区、未来时间或负延迟不能作为小时级证据；NVD 文档明确为 UTC 的时间按来源约定解析。政策及部分标准通常只有日/月精度，应如实标为未知，不补午夜时间来证明达标。

至少需七类实际 AI 相关内容、足量可信时间的新漏洞样本、严格六小时违约统计、未知时间解释，以及持续运行、漏采检查和故障恢复记录。空样本显示 0 不等于达标；已观察样本均小于六小时不保证未知、漏采、上游迟发布或未来内容也满足要求。逐源 `fresh` 只说明最近轮询状态，不能代替内容覆盖或发布时间延迟。

## 4. 主系统接入仍需 A/C 完成

团队启动链为 `../main.py` → `../api/app.py` → `../agents/monitor_agent.py`。主系统仍调用顶层 NVD/OSV，并使用 `../database/store.py` 的 JSON 知识库；B 使用 `data/intelligence.db` 和默认 `127.0.0.1:8765` 查询服务。主页面和问答不会自动看到 B 的融合、分类或文档结果。

已有 CVE 交接方式：

1. A 在主监测来源注册处调用 `../collectors/intelligence.py` 的 `IntelligenceCollector.collect()`，复用团队既有采集→富化→入库流程。
2. 主后端调用 `GET /api/intelligence/team`，写入团队知识库，供页面和问答使用。

这两种方式读取本地 B API，不自动触发外部采集；适配器尚未在主流程注册。默认返回当前有效、已完成分类的 AI 正例；查全部漏洞或待复核结果需明确使用 `ai_only=false`、`include_review=true`。分类未完成时默认 AI 列表为空是预期行为。

非 CVE 接口 `GET /api/documents`、`/api/documents/stats`、`/api/documents/{document_id}` 已实现。文档保留来源类别、类型、标题/摘要、URL、发布时间精度、首次入库、原始证据及可选关联 CVE。A/C 还需将 `document_id/content_type` 等字段接入主数据模型、知识库、富化、索引和页面，并建立论文/标准/政策与漏洞或产品的引用关系。不能把无 CVE 文档硬塞为虚构漏洞，也不能将 B 文档 API 可查询等同于主系统已能检索问答。

联调验收至少包括：同一 CVE 只展示一条，多源证据可查看，CVSS/影响范围/修复版本保留；分类哈希/版本变化后不继续展示过期正例；无 CVE 文档可入主库、检索、看原文和引用；中文搜索、详情和问答能使用新记录。完成前状态应写为“B 独立服务和交接接口已实现，主流程集成待完成”。

## 5. 下一步按优先级执行

### P0：真实采集、严格时效和主系统集成

- 已完成真实多源单轮；继续按源核验内容、分页/窗口完整性与首次入库时间，不只看退出码。保留恢复采集时的六小时超限记录，不重置基线或时间戳。
- 持续运行 `python run_monitor.py`，默认每 15 分钟一轮；保存来源日志、`monitoring_status.json`、健康、覆盖和 CVE 指标响应，验证新样本、失败隔离、恢复与积压消化。
- 每轮默认自动运行 V5 分类，条数预算 300、模型预算 0、分类超时 90 秒；采集与分类结果分别检查。积压较多时另跑 `python run_ai_classification_v5.py --max-items 300 --max-llm-calls 0`。旧 `run_monitor_once.py` 保留三源兼容用途，不是新八类默认入口。
- 与 A 完成 CVE 适配器注册，与 A/C 完成非 CVE 主数据模型及证据检索接入，验证采集→富化→索引→页面/问答的闭环。
- 建立独立人工标注评测集：AI 正例、词语相似的非 AI 负例、边界案例和无 CVE 文档。分别报告规则、语义判断与最终流水线的 Precision、Recall、待复核率；评测集与规则调优数据分离。

模型自报 `confidence`、处理数量和测试数量都不等于准确率。15 分钟轮询、120 秒单源超时和近期优先是时效工程措施，实际延迟仍受上游发布、限流、分页预算和断网影响，不能预先承诺真实 SLA。

### P1：完善已实现来源的线上覆盖与证据

论文、标准、政策、博客、社区与厂商采集及文档模型已实现，后续重点是逐源真实验证和覆盖缺口，而不是继续将这些能力写成“尚无采集器”。记录每类实际内容、稳定 ID、来源发布时间精度、更新检测、分页完整性、过滤误差和来源独立性。

扩大 arXiv 旧论文修订覆盖需另行设计更新查询；验证 RSS 保留窗口和历史恢复、NIST 目录发现完整性、政策 API 全分页预算。明确上游只有摘要而非全文的来源，不能将摘要或 HTML 原文存储描述为已完成全文语义知识底座。

### P2：部署与监测工程化

`Dockerfile` 和 `compose.yml` 提供 B 独立容器部署；在仓库根目录执行：

```bash
docker compose -f intelligence/compose.yml up -d --build
docker compose -f intelligence/compose.yml ps
docker compose -f intelligence/compose.yml logs -f
```

`monitor` 与 `api` 服务分别运行于 B 的 `/app`，共用 `/app/data` 持久化 SQLite/状态/日志数据卷，宿主机 API 仅绑定 `127.0.0.1:8765`。该 Compose 不启动团队主应用或自动完成 A/C 接入。停止使用 `down`，不要用 `down -v` 删除已存证据。宿主机可用独立虚拟环境运行，同样需守护监测和 API 两个进程。

仍需来源级失败/超时/积压告警、限流和接口变化诊断、备份/恢复、CI 与长期运行记录。测试暂时断网、重复批次、子进程超时、进程重启、SQLite 并发和积压恢复；部署文件存在不等于已证明稳定性或自动运维。

## 7. 比赛指标对照与当前目标

以下为赛题 PDF 阈值，属于评审标准，不是当前得分预测。用户当前验收采用更严格的 **漏洞延迟 `<6h`**，不能把 PDF 的 `≤6h` 当作这次目标。

| 初赛指标 | 合格 | 良好 | 优秀 |
| --- | --- | --- | --- |
| 监测完整性，15 分 | 至少 3 类，9 分 | 5 类以上，12 分 | 7 类以上且含实时监测，15 分 |
| 富化完整性，15 分 | 至少 3 维，9 分 | 5 维以上，12 分 | 信息准确且含自动关联推理，15 分 |
| 问答完整性，15 分 | 基础关键词检索，9 分 | 语义理解与多轮，12 分 | 跨文档推理与深度分析，15 分 |
| 监测时效，5 分 | ≤24 小时，3 分 | ≤12 小时，4 分 | ≤6 小时，5 分 |
